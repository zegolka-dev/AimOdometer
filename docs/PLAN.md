## 0. Цели

1. Точно считать **физический путь мыши по коврику** (Raw Input → отсчёты сенсора → см), а не путь курсора, в том числе в шутерах с захваченным курсором.
2. Работать постоянно в фоне **незаметно**: ≤ 15 МБ private working set, ≈0% CPU в простое, < 0.5% одного ядра при 8000 Гц в игре, без влияния на задержку ввода.
3. **Безопасно для античитов**: никаких хуков, инъекций, оверлеев, чтения памяти.
4. **Приватно**: клавиатура не читается вообще; без входа — ноль сетевых запросов (кроме отключаемой проверки обновлений и явно открытой вкладки «Карта», см. допущение A12).
5. Весёлая статистика, ачивки, карта «куда бы ты дошёл», а после входа через Steam — синхронизация между ПК, друзья и рейтинги.
6. Распространение только через GitHub (Releases + лендинг на Pages), автообновление.

## 2. Архитектура

### 2.0 Как это выглядит для пользователя

- После установки и при каждом входе в Windows AimOdometer **сам запускается в фоне**: видна только иконка в трее, окна нет. Статистика считается всё время.
- **Клик по иконке в трее** (левая кнопка), ярлык в меню «Пуск» или на рабочем столе, повторный запуск exe → **открывается окно приложения** со статистикой и всеми функциями (Обзор, Игры, Статистика, Карта, Ачивки, Друзья, Снаряжение, Настройки).
- Правая кнопка по иконке → меню: Открыть · Пауза · Настройки · Выход.
- **Крестик на окне** закрывает только окно; подсчёт в фоне продолжается. Полностью выключить — «Выход» в меню трея.
- Технически это два процесса (фоновый счётчик и окно), но для пользователя это **одно приложение**: одна иконка, один установщик, одно имя в автозагрузке. Разделение нужно, чтобы в фоне всегда висело ~10 МБ, а не ~150 МБ, которые занимает окно со статистикой.

### 2.1 Процессы и потоки данных

```
                       ┌──────────────────────────────────────────────┐
  Мышь(и) ──Raw Input──▶ AimOdometer.Tracker.exe  (NativeAOT, Win32)  │
  (WM_INPUT,           │  • скрытое top-level окно (никогда не показ.) │
   RIDEV_INPUTSINK)    │    – Raw Input + трей + широковещательные    │
                       │      сообщения (сон, выход из сеанса, время) │
  SetWinEventHook ────▶│  • накопители в памяти (без аллокаций)       │
  (EVENT_SYSTEM_       │  • сброс в SQLite раз в 60 с / сон / выход   │
   FOREGROUND)         │  • named pipe-сервер (живой счётчик, команды)│
                       │  • балун-уведомления трея (ачивки)           │

                               ▼                       ▼

                       ┌───────┴───────────────────────┴──────────────┐
                       │ AimOdometer.App.exe  (WPF, .NET 10)          │
                       │  • запускается по клику, закрывается целиком │
                       │  • сопоставление exe → игра, статистика      │
                       │  • WebView2 + MapLibre только на вкладке Карта│
                       │  • AimOdometer.Cloud: Steam-вход, синхрониз. │
                       └───────┬──────────────────────────────────────┘

                               ▼

              Steam OpenID / Web API (ключ только на сервере)
              OpenFreeMap / Nominatim / OSRM (только вкладка «Карта»)
              GitHub Releases (Velopack, проверка обновлений)
```

**Почему не чистое message-only окно (`HWND_MESSAGE`).** Message-only окна **не получают широковещательные сообщения**: `WM_POWERBROADCAST`, `WM_QUERYENDSESSION`/`WM_ENDSESSION`, `WM_TIMECHANGE`, `WM_SETTINGCHANGE`, `TaskbarCreated` (перерисовка трея после перезапуска Explorer). Поэтому трекер создаёт **одно скрытое top-level окно** (без `WS_VISIBLE`, с `WS_EX_TOOLWINDOW`, никогда не показывается и не берёт фокус) — оно получает и Raw Input с `RIDEV_INPUTSINK`, и все системные события. Это осознанное отступление от буквы ТЗ ради его же требований (сон, завершение сеанса, смена часового пояса).

### 2.2 Горячий путь трекера

1. `WM_INPUT` → `GetRawInputBuffer` в цикле в заранее выделенный буфер (64 КБ, `NativeMemory`) → разбор `RAWINPUT` прямо в памяти (учитываем выравнивание `NEXTRAWINPUTBLOCK`).
2. Для каждой записи мыши: `MOUSE_MOVE_ABSOLUTE` → отдельный счётчик «absolute» (не путь); иначе `dx, dy` → `path += sqrt(dx²+dy²)`, `|dx|`, `|dy|` в `double`; флаги кнопок → счётчики кликов; `usButtonData` → колесо (в «щелчках» по 120).
3. Индекс устройства: `hDevice` → номер слота через маленький массив (≤ 16 мышей), новые устройства резолвятся вне горячего пути (`GetRawInputDeviceInfo` + `RIDI_DEVICENAME` один раз, `WM_INPUT_DEVICE_CHANGE`).
4. Текущий «ведро» = (слот мыши × текущий app-id × текущий локальный час). Смена часа проверяется сравнением `QPC >= nextBoundaryTicks` (одно целочисленное сравнение на пачку).
5. Флик-скорость: кольцевой буфер (QPC, path) на устройство, **окно 50 мс**. Обоснование: фоновые сообщения в Win11 приходят ~раз в 8 мс → в окне 6+ отсчётов (меньше — шум); флик длится 100–250 мс, поэтому 50 мс не «размазывает» пик. Скорость = Σpath за окно / фактическую длительность окна.
6. Никаких строк, LINQ, боксинга, `new` в этом пути. Проверяем тестом: `GC.GetAllocatedBytesForCurrentThread()` до/после 1 млн синтетических событий = 0.

### 2.3 Модель локальных данных (SQLite, WAL)

- `devices(id, device_path, vid, pid, display_name, dpi, is_touchpad, excluded, first_seen, last_seen)`
- `apps(id, exe_path, exe_name, first_seen)` — трекер хранит только это; что это за игра — решает UI.
- `hourly(local_date, local_hour, utc_offset_min, device_id, app_id, dpi, path_counts, x_counts, y_counts, abs_events, clicks_l, clicks_r, clicks_m, clicks_x1, clicks_x2, wheel_notches, move_seconds, fg_seconds, peak_speed_counts_s)` — PK (local_date, local_hour, utc_offset_min, device_id, app_id); upsert с суммированием.
  - Храним **локальную дату и час на момент события** + смещение UTC → полночь, DST и смена пояса обрабатываются однозначно: «день» = календарный день там, где был пользователь.
  - Храним **отсчёты, а не сантиметры**, а DPI — в каждой строке (входит в ключ) → смена DPI действует «с этого момента», а исправить прошлое (с подтверждением) можно одним UPDATE. *(Изменено в фазе 2: отдельная таблица `dpi_history` не нужна.)*
- `settings`, `game_rules` (ручные правила), `geocode_cache`, `route_cache`, `achievements_unlocked`, `gear_pads`, `gear_mice`, `sync_state`.
- Миграции схемы — версионированные SQL-скрипты в Core, `PRAGMA user_version`.
- Объём: ~24 строки × (мыши × приложения) в день → единицы МБ в год.

### 2.4 Межпроцессное взаимодействие

- UI читает SQLite напрямую (WAL: чтение не блокирует запись).
- Named pipe `\\.\pipe\AimOdometer-<SID>` с ACL «только текущий пользователь». Бинарный протокол: `GetLive` (несброшенные счётчики), `Subscribe` (раз в 250 мс, только пока UI открыт — **таймер живёт только пока есть подписчик**), `ReloadSettings`, `Pause(min)`, `Resume`, `Flush`, `Shutdown` (для обновления).

### 2.6 Безопасность Steam-входа (итоговый поток)

1. App: генерирует `state`, `code_verifier` (32 байта), `code_challenge = BASE64URL(SHA256(verifier))`; поднимает `HttpListener` на `http://127.0.0.1:<случайный порт>/callback/`; открывает браузер на `…/functions/v1/auth-steam/start?state&challenge&port`.
2. Edge Function `start`: сохраняет `(state, challenge, port, expires=5 мин)` в таблицу `auth_pending`, редиректит на `https://steamcommunity.com/openid/login` с `return_to=…/auth-steam/callback?state=…`.
3. `callback`: проверяет `openid.return_to`, `openid.op_endpoint`, делает `check_authentication` у Steam, извлекает SteamID64 из `claimed_id` (строгий regex), создаёт/находит пользователя (`steam_<id>@users.aimodometer.invalid`, `email_confirm=true`, публичные email-регистрации в проекте выключены), сохраняет одноразовый `code` (хэш, 60 с), редиректит на `http://127.0.0.1:<port>/callback/?code&state`.
4. App сверяет `state`, POST `auth-steam/exchange {code, verifier}` → функция проверяет `SHA256(verifier)==challenge`, удаляет запись, вызывает `auth.admin.generateLink(magiclink)` и возвращает `token_hash` → App вызывает `POST /auth/v1/verify` → получает access + refresh токены.
5. Токены — в Windows Credential Manager через DPAPI (`ProtectedData`, scope CurrentUser).

2. **Схема локальной БД с самого начала хранит отсчёты + локальную дату/смещение + device/app id** — так фазе 7 не понадобится миграция данных, а смена DPI применима задним числом.
3. **Трекер никогда не ходит в сеть** — синхронизирует только App. Это экономит память трекера и упрощает объяснение «почему безопасно».

## 5. Чек-лист ручного античит-тестирования (фаза 2 — только CS2; фаза 9 — всё)

Для каждой игры: трекер запущен заранее; сыграть ≥ 30 мин (для FACEIT/Vanguard — ≥ 2 матчей), затем проверить:
- [ ] Игра запустилась без предупреждений античита; нет вылетов «untrusted»/kick.
- [ ] Пробег за сессию записан в статистику этой игры, сравнить с ожиданием (DPI × движения).
- [ ] FPS и задержка: сравнить средний FPS/1% low с трекером и без (CapFrameX или встроенный счётчик), разница в пределах шума.
- [ ] Ачивка в процессе игры не всплыла, появилась после выхода.
- [ ] Игры: **CS2** (VAC, + запуск с `-insecure` не нужен — проверяем обычный режим), **Apex Legends** (EAC), **Valorant** (Vanguard, после перезагрузки ПК с запущенным трекером), **FACEIT** клиент + матч, по возможности **Fortnite** (EAC/BattlEye).
- [ ] Записать результат в `docs/ANTICHEAT.md` (дата, версия, результат).

## 6. Риски и как снижаем

| # | Риск | Вероятн. | Как снижаем |
|---|---|---|---|
| R1 | Склейка Raw Input до 125 Гц в фоне (Win11) занижает путь на кривых движениях | средняя | Замер в фазе 2; при заметной ошибке — документируем поправку или опцию (точность ±X%). Склейка не теряет сумму смещений, теряется только «изгиб» внутри 8 мс. |
| R2 | NativeAOT + свой SQLite/Win32 слой — больше ручного кода | средняя | Тонкие обёртки, тесты, примеры из docs Microsoft; всё в отдельном проекте `Win32`. |
| R3 | Бюджет 15 МБ не уложится | низк.–средн. | AOT-настройки размера, ленивые структуры, `SetProcessWorkingSetSize` не используем (обман метрики); замер в каждой фазе. |
| R4 | Античит воспримет трекер подозрительно | низкая | Только пассивный Raw Input (так же работают Discord, Steam Input, драйверы мышей), без хуков; ранний тест; в будущем подпись кода. |
| R5 | Supabase поменяет поведение `generateLink`/`verify` | низк.–средн. | Изолируем в одной Edge Function; запасной план — свой OIDC-эмитент для Supabase custom OIDC provider (Edge Function как OIDC-провайдер поверх Steam). |
| R6 | Free-тариф Supabase: 500 МБ БД, засыпание через 7 дней | средняя при росте | Дневные агрегаты, сворачивание старше 90 дней в месячные, мониторинг размера; при росте — Pro или чистка. |
| R7 | OSRM demo / Nominatim заблокируют или откажут | средняя | Кэш навсегда, 1 запрос на маршрут, `services.json` для смены сервиса без релиза, запасной ORS через Edge Function. |
| R8 | SmartScreen пугает неподписанным exe | высокая до подписи | Объяснение в README/сайте, SignPath после первого релиза. |
| R9 | Пользователь меняет DPI кнопкой на мыши | высокая | Предупреждение; профили DPI с горячей клавишей — **не делаем в v1** (горячая клавиша = чтение клавиатуры/RegisterHotKey, противоречит «клавиатуру не трогаем» по духу). Вместо этого — быстрый выбор профиля DPI из меню трея. |
| R10 | Балун трея в Win11 может быть скрыт настройками «Не беспокоить» | низкая | Это ожидаемое поведение; ачивка всё равно видна в App. |
| R11 | GPU/драйверы: WebView2 без WebGL → MapLibre не рисует | низкая | Проверка и понятное сообщение; растровый fallback. |

## 9. Принятые допущения

- **A1.** Поддержка: Windows 10 22H2+ и Windows 11, только x64 (твоё решение). ARM64 — возможное расширение позже.
- **A2.** Проект — в `C:\Claude general\AimOdometer` (твоё решение).
- **A3.** Мировой рейтинг — opt-in, рейтинг друзей — opt-out (твоё решение).
- **A4.** Трекер использует скрытое top-level окно вместо `HWND_MESSAGE` (см. 2.1) — иначе не приходят события сна/завершения сеанса/смены времени.
- **A5.** «День» = локальный календарный день в месте и поясе, где было движение (храним дату и смещение UTC на момент события). Если пользователь перелетел через пояса, у дня может быть 23 или 25 «часов» — это нормально.
- **A6.** Средние: показываем «в среднем за активный день» (крупно) и «в среднем за календарный день» (мелко, с подсказкой).
- **A7.** Колесо: 1 «щелчок» = 120 единиц `WHEEL_DELTA`; для колёс с плавной прокруткой копим дробные значения.
- **A8.** Тачпад определяется автоматически и учитывается как отдельное устройство; исключить можно в настройках.
- **A9.** Трекер **никогда** не обращается к сети. Синхронизация — только из App (при открытии, раз в 15 мин пока открыт, при закрытии). Значит, данные с ПК, где App давно не открывали, придут в облако при следующем открытии. Если тебе важна фоновая синхронизация — можно позже добавить её в трекер (≈ +2–4 МБ памяти).
- **A10.** Профили DPI с горячей клавишей — не делаем (см. R9); вместо них — переключение профиля из меню трея.
- **A11.** Установка через Velopack в `%LOCALAPPDATA%\AimOdometerApp\`, данные — в `%LOCALAPPDATA%\AimOdometer\` (как в ТЗ), они переживают переустановку.
- **A12.** Вкладка «Карта» — единственное исключение из «без входа нет сети»: при её открытии загружаются тайлы/геокодинг/маршрут. Это явно описано в PRIVACY и в самой вкладке (кнопка «Загрузить карту» при первом открытии).
- **A13.** Уведомления об ачивках — балуны трея (выглядят как тосты Windows), а не WinRT-тосты (подробно в 2.5).
- **A14.** Иконки игр после входа — из публичного Steam CDN по AppID (без ключа); без входа — только из exe.
- **A15.** Сайт: лёгкий статический HTML/CSS/JS без фреймворков, домен `<твой-ник>.github.io/AimOdometer`.
- **A16.** Версионирование SemVer, первый публичный релиз — `v0.1.0` после фазы 9; до этого — пред-релизы для тебя.
- **A17.** Сервисный email пользователей Supabase вида `steam_<id>@users.aimodometer.invalid` — никогда не используется для писем; email-регистрация в проекте выключена.
